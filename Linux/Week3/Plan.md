# 🤔​ 이번 주 목표

이번 주는 Linux 커리큘럼의 다섯 번째, 여섯 번째 챕터, **"사용자 관리"**와 **"Process"**를 다룬다. 2주차에서 소유자(Owner)/그룹(Group) 개념으로 "누가 파일에 접근할 수 있는가"를 배웠다면, 이번 주는 그 "누가"에 해당하는 사용자와 그룹을 직접 만들고 관리하는 방법을 배운다. 그리고 후반부에서는 시선을 파일에서 실행 중인 프로그램으로 옮겨, 하나의 명령을 실행했을 때 리눅스 내부에서 어떤 일이 벌어지는지(Process)를 이해한다. 사용자 관리와 프로세스는 서로 무관해 보이지만, 사실 모든 프로세스는 반드시 "어떤 사용자의 권한으로" 실행되기 때문에 이 둘은 한 주 안에서 자연스럽게 연결된다.

---

## 🫵​ 월요일

### 학습 목표
리눅스에서 사용자와 그룹이 어떻게 생성되고 저장되는지 이해하고, 실제로 새로운 사용자·그룹을 만들어본다. 2주차에 배운 소유자/그룹 개념이 실제로 어디서 만들어지는지 연결해서 이해한다.

### 배울 개념
- **useradd** : 새 사용자 계정 생성 (`-m` 홈 디렉토리 생성, `-s` 로그인 쉘 지정, `-G` 보조 그룹 지정)
- **usermod** : 기존 사용자 계정 정보 수정 (`-aG` 그룹 추가, `-s` 쉘 변경)
- **groupadd** : 새 그룹 생성
- **/etc/passwd, /etc/group, /etc/shadow** : 사용자·그룹·비밀번호 정보가 저장되는 시스템 파일

### 실습
```bash
sudo groupadd dev                          # dev 그룹 생성
sudo useradd -m -s /bin/bash devuser        # 홈 디렉토리 포함 사용자 생성
sudo usermod -aG dev devuser                # devuser를 dev 그룹에 추가
cat /etc/passwd | grep devuser              # 사용자 정보 확인
cat /etc/group | grep dev                   # 그룹 소속 확인
```

**예상 결과**
```
$ cat /etc/passwd | grep devuser
devuser:x:1001:1001::/home/devuser:/bin/bash

$ cat /etc/group | grep dev
dev:x:1002:devuser
```

**왜 이렇게 되는가**
`/etc/passwd`에는 사용자 이름, UID, GID, 홈 디렉토리, 로그인 쉘 같은 "공개 정보"만 저장된다. 실제 비밀번호 해시는 `/etc/shadow`라는 별도 파일에 저장되는데, 이 파일은 root만 읽을 수 있도록 `600` 권한이 걸려 있다. 왜 굳이 분리했을까? `/etc/passwd`는 `ls -l`처럼 사용자 이름을 UID로 변환하는 등 여러 프로그램이 항상 읽어야 하는 파일이라 누구나 읽을 수 있어야 하는데, 만약 비밀번호 해시까지 같이 들어있다면 오프라인 크래킹에 노출되기 때문이다. 2주차에 배운 "파일과 권한" 원리가 시스템 파일 자체의 설계에도 그대로 적용된 셈이다.

### 오늘 꼭 기억해야 하는 내용
- `useradd -m` = 사용자 생성 + 홈 디렉토리 자동 생성, `usermod -aG` = 기존 그룹을 유지하면서 새 그룹 추가
- 사용자 정보(`/etc/passwd`)와 비밀번호 해시(`/etc/shadow`)는 보안을 위해 별도 파일로 분리 저장된다

## 🫵​ 화요일

### 학습 목표
사용자가 자신의 비밀번호를 바꾸는 원리와, 일반 사용자가 임시로 관리자 권한을 빌려 쓰는 `sudo` 메커니즘을 이해한다.

### 배울 개념
- **passwd** : 사용자 비밀번호 설정/변경 (1주차에 배운 SUID 덕분에 일반 사용자도 실행 가능)
- **sudo** : 지정된 사용자가 명령어 하나를 관리자(root) 권한으로 실행할 수 있게 해주는 도구
- **/etc/sudoers, visudo** : sudo 권한 설정 파일과, 이를 안전하게 편집하는 전용 명령어
- **su vs sudo** : `su`는 완전히 다른 사용자로 전환, `sudo`는 명령어 하나만 잠깐 권한을 빌려 실행

### 실습
```bash
sudo passwd devuser              # devuser의 비밀번호 설정
sudo usermod -aG sudo devuser     # devuser에게 sudo 권한 그룹 부여 (Ubuntu 기준)
sudo visudo                       # sudoers 파일을 안전하게 편집

su - devuser                      # devuser로 완전히 전환 (비밀번호 필요)
sudo whoami                       # devuser 계정에서 sudo로 실행 시 root로 표시되는지 확인
```

**예상 결과**
```
$ sudo whoami
root
```

**왜 이렇게 되는가**
`passwd`가 일반 사용자 권한으로도 실행되는 이유는 1주차에 배운 SUID 덕분이다 — 실행 파일 자체에 SUID가 걸려 있어, 누가 실행하든 "소유자(root)의 권한"으로 잠깐 실행되어 `/etc/shadow`를 수정할 수 있다. `sudo`는 이 개념을 확장한 것으로, `/etc/sudoers`에 등록된 사용자만 명령어 앞에 `sudo`를 붙여 그 한 줄만 root 권한으로 실행하고 즉시 원래 권한으로 돌아온다. `su -`처럼 아예 다른 사용자로 로그인 세션 자체를 바꾸는 것과는 위험도가 다르다. `visudo`를 쓰는 이유는 `/etc/sudoers`에 문법 오류가 생기면 시스템 전체에서 sudo가 막힐 수 있는데, `visudo`는 저장 전에 문법을 검사해 이런 사고를 막아준다.

### ⚠ 위험한 명령어 주의
`/etc/sudoers`를 `visudo` 없이 일반 편집기로 직접 수정하다가 문법 오류가 나면, 재부팅 전까지 어떤 사용자도 `sudo`를 쓸 수 없게 될 수 있다. 또한 `NOPASSWD:ALL` 같은 설정을 습관적으로 넣으면, 계정이 탈취됐을 때 비밀번호 확인 없이 바로 root 권한을 넘겨주는 것과 같으므로 실무에서는 최소 권한 원칙(필요한 명령어만 허용)을 지켜야 한다.

### 오늘 꼭 기억해야 하는 내용
- `passwd`가 일반 사용자로도 실행되는 이유는 SUID (1주차 개념과 연결)
- `sudo` = 명령어 하나만 임시로 권한 상승, `su -` = 세션 자체를 다른 사용자로 전환
- `/etc/sudoers`는 반드시 `visudo`로 편집한다

## 🫵​ 수요일

### 학습 목표
명령어를 실행했을 때 리눅스 내부에서 프로세스가 어떻게 생성되고 식별되는지 이해하고, 현재 실행 중인 프로세스를 조회하는 도구를 익힌다.

### 배울 개념
- **Process** : 실행 중인 프로그램의 인스턴스, 커널이 관리하는 독립적인 실행 단위
- **PID / PPID** : 각 프로세스의 고유 식별 번호(PID)와, 그 프로세스를 만든 부모 프로세스의 번호(PPID)
- **Thread** : 하나의 프로세스 안에서 동시에 실행되는 더 작은 실행 흐름 단위 (메모리 공간을 공유)
- **Daemon** : 사용자 로그인과 무관하게 백그라운드에서 지속적으로 실행되는 프로세스 (이름이 보통 `d`로 끝남, 예: `sshd`, `systemd`)
- **ps, top, htop** : 현재 실행 중인 프로세스를 조회하는 도구

### 실습
```bash
ps -ef | head            # 전체 프로세스를 PID/PPID와 함께 확인
ps aux | grep bash        # 특정 이름을 가진 프로세스 검색
pstree                    # 프로세스 부모-자식 관계를 트리로 확인
top                       # 실시간 CPU/메모리 사용량 확인 (q로 종료)
```

**예상 결과**
```
$ ps -ef | head -5
UID   PID  PPID  C STIME TTY      TIME CMD
root    1     0  0 09:00 ?    00:00:02 /sbin/init
root   612     1  0 09:00 ?    00:00:00 /usr/sbin/sshd
user  1400  1380  0 09:05 pts/0 00:00:00 bash
```

**왜 이렇게 되는가**
리눅스에서 모든 프로세스는 PID 1(보통 `systemd` 또는 `init`)을 최상위 조상으로 하는 트리 구조를 이룬다. 새 프로세스는 반드시 기존 프로세스가 `fork()`라는 시스템 콜로 자기 자신을 복제해서 만들어지기 때문에, 태어날 때부터 PPID(부모 PID)를 갖게 된다. `bash`에서 명령어를 입력하면 그 bash가 부모가 되어 자식 프로세스를 만드는 식이다. Thread는 이 프로세스 "안에서" 메모리를 공유하며 동시에 여러 일을 처리하는 단위라, 프로세스보다 훨씬 가볍게 생성/전환된다.

### 오늘 꼭 기억해야 하는 내용
- 모든 프로세스는 PID 1을 최상위 조상으로 하는 부모-자식 트리 구조를 이룬다
- 프로세스 = 독립된 메모리 공간을 가진 실행 단위, Thread = 그 안에서 메모리를 공유하는 더 작은 실행 흐름
- Daemon은 로그인 세션과 무관하게 백그라운드에서 계속 실행되는 프로세스다

## 🫵​ 목요일

### 학습 목표
프로세스가 가질 수 있는 상태(포그라운드/백그라운드/좀비)를 이해하고, 시그널을 이용해 프로세스를 안전하게 제어하는 방법을 익힌다.

### 배울 개념
- **Foreground / Background** : 터미널을 점유하며 실행되는 상태 vs `&`로 뒤에서 실행되는 상태 (`jobs`, `fg`, `bg`로 전환)
- **Zombie(좀비 프로세스)** : 자식 프로세스는 이미 종료됐지만, 부모 프로세스가 그 종료 상태를 회수(`wait()`)하지 않아 프로세스 테이블에 남아있는 상태
- **kill** : 프로세스에 시그널(signal)을 보내 종료를 "요청"하는 명령어 (`SIGTERM`, `SIGKILL` 등)

### 실습
```bash
sleep 300 &          # 백그라운드로 실행 (& : 백그라운드 실행)
jobs                  # 현재 쉘의 백그라운드 작업 목록 확인
fg %1                 # 1번 작업을 다시 포그라운드로 전환
# Ctrl+Z 로 일시 정지 후
bg %1                 # 정지된 작업을 백그라운드에서 계속 실행

ps aux | grep sleep    # PID 확인
kill -15 <PID>          # SIGTERM: 정상 종료 요청 (우선 시도)
kill -9 <PID>            # SIGKILL: 강제 종료 (최후의 수단)
```

**예상 결과**
```
$ jobs
[1]+  Running                 sleep 300 &

$ kill -15 12345
$ ps aux | grep 12345
(프로세스가 정상적으로 사라짐)
```

**왜 이렇게 되는가**
`kill`이라는 이름과 달리 이 명령어의 본질은 "시그널을 보내는 것"이다. `SIGTERM(15)`은 프로세스에게 "정리하고 스스로 종료해줘"라고 정중하게 요청하는 시그널이라, 프로그램이 열려 있던 파일을 저장하거나 연결을 정리할 기회를 준다. 반면 `SIGKILL(9)`은 커널이 프로세스를 즉시 강제로 종료시키는 시그널이라 프로그램이 정리할 틈이 없다. 좀비 프로세스가 생기는 이유는, 자식이 종료되면 커널이 그 종료 상태(exit code)를 부모가 확인할 때까지 잠깐 프로세스 테이블에 남겨두는데, 부모가 이를 제때 회수하지 않으면 죽었지만 테이블에만 남아있는 "좀비" 상태가 되기 때문이다.

### ⚠ 위험한 명령어 주의
`kill -9`(SIGKILL)를 습관적으로 먼저 쓰면, 프로세스가 파일을 저장하거나 트랜잭션을 정리할 기회 없이 강제로 죽기 때문에 데이터베이스 파일 손상이나 임시 파일 잔류 같은 문제가 생길 수 있다. 실무에서는 반드시 `kill -15`(SIGTERM)로 먼저 정상 종료를 시도하고, 일정 시간이 지나도 종료되지 않을 때만 `kill -9`를 최후의 수단으로 사용한다.

### 오늘 꼭 기억해야 하는 내용
- Foreground = 터미널을 점유, Background(`&`) = 터미널을 점유하지 않고 뒤에서 실행
- Zombie = 종료됐지만 부모가 상태를 회수하지 않아 프로세스 테이블에 남은 상태
- `kill -15`(정상 종료 요청)을 먼저 시도하고, `kill -9`(강제 종료)는 최후의 수단으로 사용

## 🫵​ 금요일

### 프로젝트 제목
**"사용자 및 프로세스 진단 스크립트"**

### 프로젝트 목표
월~목에 배운 사용자 관리 명령어(useradd, groupadd, usermod)와 프로세스 명령어(ps, kill)를 결합해, 현재 시스템의 사용자·그룹 상태와 실행 중인 프로세스를 한눈에 보여주는 진단 스크립트를 만든다.

### 구현해야 하는 기능
1. 새 사용자(예: `testuser`)와 새 그룹(예: `testgroup`)을 생성하고, `/etc/passwd`·`/etc/group`에서 생성 결과를 조회해 출력
2. `usermod`로 `testuser`를 `testgroup`에 추가하고 결과 확인
3. 현재 실행 중인 프로세스를 CPU 사용량 기준으로 상위 5개 출력 (`ps aux --sort=-%cpu | head -6`)
4. 특정 이름(예: `sleep`)을 가진 프로세스를 찾아 PID를 출력하는 기능

힌트: `#!/bin/bash`로 시작하는 스크립트 파일을 만들고, 지금까지 실습한 명령어를 순서대로 조합하면 된다. `ps aux | grep 이름`으로 특정 프로세스를 찾을 때, `grep` 자기 자신도 결과에 걸리는 경우가 있다는 점을 관찰해보자(다음 주 `grep` 챕터에서 더 다룬다).

### 사용해야 하는 Linux 기술
`useradd`, `groupadd`, `usermod`, `cat /etc/passwd`, `cat /etc/group`, `ps aux`, `grep`

## 토요일

### 프로젝트 확장
금요일 스크립트를 **인자로 사용자명과 프로세스 검색어를 받는 재사용 가능한 진단 도구**로 발전시킨다.

### 추가 기능
- 생성할 사용자 이름을 첫 번째 인자로 받기 (`./diagnose.sh testuser`)
- 검색할 프로세스 이름을 두 번째 인자로 받기 (`./diagnose.sh testuser sleep`)
- 해당 프로세스가 발견되면 PID와 함께 "종료하시겠습니까?"에 해당하는 안내 메시지를 출력 (실제 `kill`은 이번 주에는 자동 실행하지 않고, 사람이 직접 확인 후 실행하도록 안내만 출력)
- 스크립트 실행 결과를 `diagnose_log_날짜.txt`로 저장

힌트: `$1`은 첫 번째 인자, `$2`는 두 번째 인자다. 자동으로 `kill`을 실행하는 스크립트는 실무에서도 위험하게 취급되므로, 지금 단계에서는 "무엇을 종료해야 하는지 알려주는 것"까지만 구현하는 것이 안전한 설계다.

### 리팩토링 포인트
- 사용자명/프로세스명이 하드코딩되어 있지 않고 인자로 잘 분리되었는지
- 이미 존재하는 사용자를 다시 생성하려고 할 때 어떤 에러가 나는지 관찰해보기 (본격적인 에러 처리는 다음 주 Shell Script 챕터에서 다룬다. 지금은 "이 문제를 인지"만 해두면 된다)
- 프로세스를 자동으로 죽이지 않고 "안내만" 하도록 설계했는지 (안전한 자동화 습관)

# 🫵​ 이번 주 핵심 개념 5가지
1. **useradd/usermod/groupadd** — 사용자와 그룹을 생성하고 소속을 관리하는 명령어
2. **/etc/passwd vs /etc/shadow** — 공개 정보와 비밀번호 해시를 분리해 저장하는 보안 설계
3. **sudo vs su** — 명령어 단위 임시 권한 상승 vs 세션 전체의 사용자 전환
4. **Process/PID/PPID** — 모든 프로세스는 PID 1을 최상위 조상으로 하는 트리 구조를 이룬다
5. **kill -15 vs -9** — 정상 종료 요청(SIGTERM)과 강제 종료(SIGKILL)의 차이

# 실무 활용 사례
- 신규 입사자 온보딩 시 `useradd`와 그룹 정책으로 팀별 접근 권한을 표준화된 절차로 부여한다.
- 서버에 SSH로 직접 root 로그인을 막고 `sudo` 권한을 가진 개별 계정만 쓰게 해서, 누가 언제 어떤 명령을 실행했는지 감사 로그(`/var/log/auth.log`)로 추적한다.
- 배포 중인 서비스가 응답하지 않을 때 `ps aux --sort=-%cpu`로 CPU를 과도하게 쓰는 프로세스를 먼저 찾아 원인을 좁힌다.
- 애플리케이션 배포 스크립트에서 `kill -15`로 기존 프로세스를 정상 종료시킨 뒤 새 버전을 기동하는 무중단에 가까운 재시작(graceful restart)을 구현한다.
- 좀비 프로세스가 누적되는 서버를 발견하면, 좀비 자체보다 그 부모 프로세스의 `wait()` 처리 로직에 버그가 있는지 애플리케이션 코드를 점검한다.
