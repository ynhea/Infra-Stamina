월
Kernel, Shell, Distribution
Big Picture of Linux
개념 + 실습
학습 목표

리눅스가 하나의 시스템으로 어떻게 구성되어 있는지 큰 그림을 그린다. Kernel과 Shell의 관계, 그리고 Distribution의 개념을 이해한다.

배울 개념
  • Kernel — 하드웨어와 소프트웨어 사이의 중재자, 프로세스/메모리/디바이스 관리
  • Shell — 사용자 명령을 커널에 전달하는 인터페이스 (bash, zsh 등)
  • Distribution(배포판) — 커널 + 패키지 관리자 + 기본 도구 모음 (Ubuntu, CentOS, Debian 등의 차이)
실습
bash
$ uname -r          # 커널 버전 확인 (-r: kernel release 표시)
$ echo $SHELL       # 현재 사용 중인 쉘 경로 확인
$ cat /etc/os-release # 배포판 정보 확인

6.8.0-45-generic
/bin/bash
NAME="Ubuntu"
VERSION="24.04 LTS (Noble Numbat)"
왜 이렇게 되는가. uname -r은 커널이 직접 시스템 콜에 응답해서 보여주는 정보다. echo $SHELL은 로그인 시점에 설정된 환경변수를 읽는 것뿐이라, 쉘을 바꿔도 자동으로 안 바뀔 수 있다는 점을 기억해야 한다.
오늘 꼭 기억해야 하는 내용
  • Kernel = 하드웨어 제어 담당, Shell = 사용자 인터페이스. 둘은 계층이 다르다.
  • 배포판이 달라도 커널 구조의 원리는 동일하다 (패키지 관리자와 도구만 다름).
화
Boot Process, File System Hierarchy
From Power-on to Login
개념 + 실습
학습 목표

전원이 켜진 순간부터 로그인 프롬프트가 뜨기까지의 과정(Boot Process)과, 리눅스 파일들이 어떤 규칙으로 배치되어 있는지(FHS)를 이해한다.

배울 개념
  • Boot Process — BIOS/UEFI → Bootloader(GRUB) → Kernel 로딩 → init/systemd → 로그인
  • File System Hierarchy(FHS) — /, /bin, /etc, /var, /home, /usr, /tmp 등 표준 디렉토리 구조와 용도
실습
bash
$ ls -l /            # 루트 디렉토리 하위 구조 확인 (-l: 상세 정보)
$ cat /etc/fstab     # 부팅 시 마운트되는 파일시스템 목록
$ systemd-analyze    # 부팅 소요 시간 분석

Startup finished in 3.912s (kernel) + 8.221s (userspace) = 12.133s
왜 이렇게 되는가. GRUB이 커널 이미지를 메모리에 올리는 순간부터가 "kernel" 시간이고, 그 이후 systemd가 서비스를 순차/병렬로 띄우는 시간이 "userspace" 시간이다. 서버 부팅이 느릴 때 원인이 커널 로딩인지 서비스 초기화인지 이 둘을 구분해서 디버깅한다.
오늘 꼭 기억해야 하는 내용
  • 부팅 순서: BIOS/UEFI → Bootloader → Kernel → init/systemd → 로그인
  • /etc는 설정 파일, /var는 로그·가변 데이터, /bin은 필수 실행 파일이라는 역할 구분
수
inode, Directory, Mount
Everything Is a File
개념 + 실습
학습 목표

"모든 것은 파일이다"라는 철학의 실체인 inode 개념을 이해하고, 디렉토리와 마운트의 관계를 파악한다.

배울 개념
  • inode — 파일의 실제 데이터가 아니라 메타데이터(소유자, 권한, 크기, 데이터 블록 위치)를 담는 구조체
  • Directory — 사실은 "파일명 ↔ inode 번호" 매핑 테이블에 불과한 특수한 파일
  • Mount — 특정 디바이스(파티션)의 파일시스템을 특정 디렉토리 경로에 연결하는 작업
실습
bash
$ touch test.txt
$ ls -i test.txt     # inode 번호 확인 (-i: inode number 표시)
$ stat test.txt      # inode 상세 정보 확인
$ df -h               # 마운트된 파일시스템 확인 (-h: human-readable)

2621447 test.txt

  File: test.txt
  Size: 0    Blocks: 0    IO Block: 4096
Inode: 2621447  Links: 1
Access: (0644/-rw-r--r--)  Uid: (1000/user)  Gid: (1000/user)
왜 이렇게 되는가. 파일 이름은 inode를 가리키는 "이름표"일 뿐이라, 같은 inode를 여러 디렉토리에서 다른 이름으로 가리킬 수 있다(Hard Link, 내일 배움). mv가 같은 파티션 내에서 순식간에 끝나는 이유도 데이터를 옮기는 게 아니라 디렉토리의 이름표만 바꿔 달기 때문이다.
오늘 꼭 기억해야 하는 내용
  • inode = 메타데이터 저장소, 실제 파일명은 디렉토리가 별도로 매핑
  • 같은 파티션 내 mv가 빠른 이유는 데이터 이동이 아니라 inode 참조만 바뀌기 때문
목
Partition, Filesystem, Hard/Symbolic Link
Same Inode, Different Name
개념 + 실습
학습 목표

파티션과 파일시스템의 차이를 이해하고, Hard Link와 Symbolic Link의 동작 원리 차이를 명확히 구분한다.

배울 개념
  • Partition — 물리 디스크를 논리적으로 나눈 영역
  • Filesystem — 파티션 위에 데이터를 저장/관리하는 방식 (ext4, xfs 등)
  • Hard Link — 같은 inode를 가리키는 또 다른 이름 (원본 삭제해도 데이터 유지)
  • Symbolic Link — 경로 자체를 가리키는 별도 파일 ("바로가기"와 유사, 원본 삭제 시 깨짐)
실습
bash
$ lsblk                      # 디스크와 파티션 구조 확인
$ ln test.txt hardlink.txt    # 하드링크 생성
$ ln -s test.txt symlink.txt  # 심볼릭 링크 생성 (-s: symbolic)
$ ls -li test.txt hardlink.txt symlink.txt
$ rm test.txt
$ cat hardlink.txt   # 정상 출력
$ cat symlink.txt    # 링크 깨짐 → 에러

2621447 -rw-r--r-- 2 user user  0 test.txt
2621447 -rw-r--r-- 2 user user  0 hardlink.txt
2621500 lrwxrwxrwx 1 user user  9 symlink.txt -> test.txt

cat: symlink.txt: No such file or directory
왜 이렇게 되는가. Hard Link는 inode 번호(2621447)가 완전히 동일하다 — 커널 입장에서 "같은 파일"이다. Symbolic Link는 별도의 inode(2621500)를 가진 새 파일이며, 그 안에 원본의 경로 문자열만 저장되어 있다. 그래서 원본이 사라지면 심볼릭 링크는 존재하지만 가리키는 대상이 없어 에러가 난다.
⚠ DANGER
rm -rf /처럼 루트 디렉토리 전체를 재귀적으로(-r) 강제(-f) 삭제하는 명령은 시스템을 완전히 파괴할 수 있다. -f 옵션은 확인 프롬프트 없이 바로 삭제하므로 절대 습관적으로 붙이지 않는다.
오늘 꼭 기억해야 하는 내용
  • Hard Link = 동일 inode 공유, Symbolic Link = 경로를 가리키는 별도 파일
  • 파티션(물리적 분할) vs 파일시스템(그 위의 논리적 관리 방식)은 다른 개념

월~목에 배운 개념(커널/쉘 정보, FHS, inode, 마운트, 링크)을 하나의 쉘 스크립트로 조사하고 보고서 형태로 출력하는 진단 도구를 만든다.

구현해야 하는 기능

금요일 스크립트를 재사용 가능한 진단 도구로 발전시킨다. 매번 하드코딩된 경로 대신, 실행할 때 원하는 디렉토리를 인자로 받아 검사할 수 있게 만든다.

추가 기능
  1. 스크립트 실행 시 인자로 디렉토리 경로를 받기 (./inventory.sh /var/log)
  2. 실행 결과를 화면 출력뿐 아니라 report_날짜.txt 같은 파일로도 저장
  3. 부팅 소요 시간(systemd-analyze)도 리포트에 포함
힌트: 쉘에서 $1은 "스크립트 실행 시 첫 번째 인자"를 의미한다. 출력을 파일로 저장하려면 > 리다이렉션을 활용해보자.
리팩토링 포인트

Sheet Summary — 이번 주 종합 정리
이번 주 핵심 개념 5가지
  1. Kernel vs Shell — 하드웨어 제어 계층과 사용자 인터페이스 계층의 분리
  2. Boot Process — BIOS/UEFI → Bootloader → Kernel → systemd 순서
  3. FHS — 표준화된 디렉토리 구조와 각 디렉토리의 역할
  4. inode — 파일의 실체는 메타데이터 구조체이며, 파일명은 별도 매핑일 뿐
  5. Hard Link vs Symbolic Link — 동일 inode 공유 여부의 차이
실무 활용 사례
  • 서버 부팅 지연 트러블슈팅 시 systemd-analyze로 커널 로딩 지연인지 서비스 초기화 지연인지 먼저 구분한다.
  • 디스크 공간이 꽉 찼다는 알림이 왔을 때 df -h로 마운트 포인트별 사용량을 확인하고, /var/log처럼 로그가 쌓이는 디렉토리를 우선 점검한다.
  • 배포 스크립트에서 심볼릭 링크(current → release-20260721)를 이용해 무중단 배포를 구현한다.
  • 설정 파일 백업 시 Hard Link를 활용하면 같은 파티션 내에서 디스크 공간을 추가로 쓰지 않고도 스냅샷을 만들 수 있다.
